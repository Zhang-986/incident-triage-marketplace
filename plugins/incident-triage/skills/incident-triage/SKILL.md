# 团队告警排查

## 第一次用，或换电脑

用户说安装、配置或验收时，主动完成下面的步骤。用户直接贴告警时，先查已可用的来源，只在需要时补配置。

1. 识别系统、架构和已有工具，复用现有配置。检查 openobserve-cli、Git、aliyun 是否可运行。缺工具时，从项目发布页或官方渠道选择当前系统适用的用户级安装方式，安装后执行版本命令确认。遇到缺管理员权限或网络失败时，给出当前系统下一步能执行的命令，并继续验证其他工具。
2. OpenObserve 优先复用公司配置。缺配置时从用户提供的告警链接取得实例和组织，缺少时请用户提供。需要登录时启动 auth login --browser，引导用户在弹窗完成公司登录，然后执行 auth status。取一条用户可访问的日志做有界查询，区分登录成功和日志流有权限。配套 openobserve Skill 已有时按它的用法操作；没有时可用 openobserve-cli skill install --agent codex 安装。
3. GitLab 优先使用当前业务仓库，以 git ls-remote 验证远端读取。没有仓库时，向用户说明需要仓库地址，拿到后可克隆到用户选定的位置。遇到 SSH 或账号鉴权失败时，告诉用户在哪完成授权，随后重试。
4. 阿里云 CLI 复用个人 profile。用 aliyun sts GetCallerIdentity 验证登录。已有目标实例时分别试读慢日志和 DMS 元数据。只验证到登录时，将实例查询权限标为待验证。需要用户登录时，引导其通过公司认可的登录方式操作，继续其他检查。
5. 用简短表格汇报每项的状态和下一步，区分工具已安装、账号已登录、数据已读通。只让用户处理必须由本人完成的登录、授权或无法推断的配置。凭据由用户在浏览器或 CLI 中输入，别让用户在聊天里贴密码、Token 或 AccessKey。

安装来源：[OpenObserve CLI](https://github.com/AngelMsger/openobserve-cli/releases)、[Git](https://git-scm.com/install/)、[阿里云 CLI](https://www.alibabacloud.com/help/zh/cli/install-cli)。

## 怎么提交告警

- 优先让用户直接贴 OpenObserve 告警链接。如果链接只有最近几小时之类的相对窗口，且告警已经过了该窗口，再请用户补发生时间。
- 没有链接时，贴告警原文即可。最有用的是环境、服务、发生时间和 trace_id。有堆栈或接口路径也可以一起贴。
- 部署 SHA、数据库实例、慢日志和执行计划按需核对。现有权限能查就直接查，只有会改变判断且查不到时再问用户。

## 从告警到证据

1. 从告警提取环境、服务、绝对时间、日志流和 trace_id。链接给出相对时间时，优先用告警时间。解析链接内的查询仅用于提取过滤条件，验证 trace_id 格式。以分钟级窗口调用 OpenObserve CLI search run，限定日志流、过滤条件和结果数。记录开始时间、报错时间、节点、接口、异常根因和关键栈帧。避免输出手机号、请求令牌或完整敏感入参。
2. 从部署记录确定当时的提交 SHA。缺部署版本时，核对业务线和环境后，用 git ls-remote --exit-code <远端> refs/heads/<分支> 取当前 SHA，再用 git fetch --no-tags --no-write-fetch-head --refmap= <远端> <SHA> 读取对象。按 SHA 用 git grep、git show 或 git diff 沿接口到 Mapper 定位。记录代码位置和 SHA，说明版本依据。查热修时同时看提交祖先关系和实际代码，兼顾 cherry-pick。只读工作区和 Git 引用，无需切换分支。
3. SQL 耗时、连接中断或疑似锁等待时，核实实际数据库实例和库名，再读 PolarDB 或 RDS 的 DescribeSlowLogRecords。把应用时间转换为 API 要求的 UTC 格式，限制时间窗并按需翻页。按数据库、来源 IP、SQL 特征和时间匹配，记录耗时、扫描行数、返回行数和锁等待。匹配多条时保留歧义；慢日志时间口径不同或未知时标明。单行查询返回多行之类的问题优先用异常栈和查询条件判断，需要时查约束元数据。
4. 用 DMS ListInstances、ListDatabases、ListTables 确认目标，再用 ListIndexes 或表元数据核对索引及列顺序。核对实际走的索引时优先用已有执行计划。生产排查全程只读，不执行原业务 SQL 或 EXPLAIN ANALYZE，不改数据、配置、告警和部署。
5. 给出事件经过、已确认的影响范围、按置信度标注的归因，以及建议修改的位置和验收方式。把代码修复存在、已合入、已部署和已验收分别核实。明确缺哪项证据可以提升置信度。

## 置信度

对每条主要结论单独标注，并写一句证据或缺口。

| 标记 | 何时使用 |
| --- | --- |
| 高 | 证据直接支持结论，例如异常栈明确报单行查询返回两行，或部署版本与复现结果都已核对。 |
| 中 | 多条证据指向同一原因，仍缺关键因果证据，例如慢日志与 SQL 特征吻合，但应用断连的触发层未确认。 |
| 低 | 有单一间接迹象或多个可行解释，写清需要查什么才能区分。 |
| 未验证 | 所需证据缺失，例如无部署记录，无法判断修复是否已在灰度运行。 |

同一个事件里，异常类型可以是高置信度，触发原因是中置信度，修复部署状态也可以未验证。用日志时间、trace_id、提交 SHA、慢日志指标或执行计划支撑判断。
